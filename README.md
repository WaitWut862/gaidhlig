# Passage

> A linguistic research tool for Scottish Gaelic — search words, sentences, and grammar rules, with morphological analysis powered by UDPipe.

Passage is a linguistic research tool for Scottish Gaelic, and the first iteration (v1) of a larger language learning platform in development. What you see here is the querying layer; the data and interface will likely change substantially by later versions.

#### Video Demo


## Features

- Search across 17,000+ lemmas, 1,200 example sentences, and 342 grammar rules
- Filter results by part of speech, CEFR difficulty, and grammar category
- Token-level morphological breakdown for every sentence, powered by UDPipe and the CoNLL-U format
- Word entries include definitions, inflected forms, synonyms, derived words, etymology, and IPA pronunciation where available
- Infinite scroll for search results
- Interface for devs to read, write, verify, and delete rules which were generated by AI


## Project Structure

**Root**
- `go.mod` / `go.sum` — Go module definition and dependency checksums
- `LICENSE` — CC BY-SA 4.0 license
- `README.md` — this file

**`cmd/main.go`**
The entry point for the web server. Initializes the database connection, registers all HTTP routes, defines the `App` struct that holds the database connection, and implements all request handlers.

**`internal/gaidhlig/`**
Contains all data and tooling specific to the Scottish Gaelic module.

- `gaidhlig.db` — the SQLite database
- `gla/` — the Gàidhlig Linguistic Analyser bridge. UDPipe has a Python binding but no Go binding, so `analyse.py` wraps UDPipe and `gla.go` calls it as a subprocess, exposing native Go functions that return CoNLL-U parse results. `scottish_gaelic.udpipe` is the UDPipe model file.
- `parsers/akerbeltz/` — scrapes Akerbeltz grammar articles, strips HTML, and uses AI to extract structured grammar rules for insertion into the database
- `parsers/dwelly/` — reads Dwelly's Gaelic-English Dictionary in plain text form and extracts word entries not already present in the database
- `parsers/kaikki/` — reads the kaikki.org Scottish Gaelic JSON dictionary and distributes the data into the database according to the schema
- `parsers/sentence_ingest/` — takes a sentence string, passes it through the GLA for morphological analysis, and stores both the sentence and its token-level analysis in the database
- `rule_manager/` — a standalone developer tool providing a GUI to read, verify, edit, and delete grammar rules in the database

**`internal/web/`**
The web application layer.

- `db/` — query functions organized by content type (`words.go`, `sentences.go`, `rules.go`). These functions are called by the handlers in `main.go` to retrieve data from the database and return it as Go structs.
- `static/style.css` — all styling for the application
- `templates/` — HTML templates rendered server-side. `base.html` is the full page shell. `results_*` templates render a full search panel response including filters. `items_*` templates render only result rows for infinite scroll loads. `word.html`, `sentence.html`, and `rule.html` are detail view fragments loaded into the right panel on click.


## Design Decisions
### Python/Flask vs Go
Having worked with Flask and Python in previous CS50 projects, I was initially conflicted as to whether I should use Flask or host the server with Go. I ended up going with Go because, although it is less intuitive to use for hosting a server, I am more comfortable working with Go from personal projects, and I intended to write the rest of the program in Go anyway. However, for the same reasons that Go is less intuitive, it was also more informative on how hosting a server actually works, so there was the added educational benefit.

### HTMX
For the frontend, I wanted to avoid writing JavaScript where possible. It is my preference to handle logistics and the workings of the website purely from backend, as I feel it results in an overall cleaner system. Admittedly, there are flaws with this angle, such as a reduced capacity for dynamism on the user side, but HTMX offered a clean way of solving these problems. HTMX's method of replacing and inserting snippets of HTML align well with my design and vision for this project.

### SQLite
SQLite was a natural fit for this project. As a self-contained, file-based database it requires no separate server process, which suits a local research tool well. It also integrates cleanly with Go via the go-sqlite3 driver, and having worked with it throughout CS50 gave me the bandwidth to focus on more complex and project specific problems.

### Polymorphic Schema
Several tables in the schema — tag_associations, rule_associations, and others — use a polymorphic pattern, storing a target_table and target_id column instead of a fixed foreign key. This allows a single tag or rule to be associated with any content type in the database — a word, a sentence, an expression — without requiring a separate join table for each relationship. Language itself is dynamic and interconnected in ways that resist rigid relational structure, and this pattern felt like the most honest way to reflect that in the schema.

### Gathering Data
To populate the db, I first went with kaikki as my main source of word data because it contained all of the information I originally wanted to include in the project, and it was in general very high quality data. However, I was disappointed to find out that it covered only a small portion of the total Gàidhlig vocabulary, so I did my best to fill in the gaps with the lower quality but larger data source, Dwelly. This widened the dataset considerably, at the cost of scattering in incomplete entries, proverbs, and phrases that don't really belong in a clean lexicon — a tradeoff I made deliberately to prioritize coverage.
Populating rules was a different challenge altogether, as I was unable to find a comprehensive dataset of Gàidhlig grammar rules. I wound up with the conclusion that the fastest and easiest way to populate my rules would be to have an AI pull them from an online article based resource, Akerbeltz. This ended up working better than expected, but left massive, and frankly hard to identify, gaps in what grammar rules are covered. The Akerbeltz articles generally cover more interesting topics, so basics and more mundane aspects of the language are left unmentioned.

### Analyzing Sentences
In my original design for this project, I had hoped to make a program which could parse Gàidhlig sentences and break them down into their POS and relative roles in the sentence, but it seemed too ambitious a goal for v1. However, I happened upon 'The Gaelic Linguistic Analyser' (GLA) while researching, which is a web tool accomplishing the very goal I had previously hoped to. The engine powering it, UDPipe, happened to be a free and downloadable tool I was easily able to use in my project. Parsing sentences was now a task which had been done for me, but UDPipe only supports Python binding, so I wrote a small script to translate the output into native Go.


## Tech Stack

- **Go** — server and routing via `net/http`
- **SQLite** — database
- **HTMX** — frontend interactivity without a JavaScript framework
- **UDPipe** — morphological analysis and CoNLL-U parsing


## Data Sources

- **kaikki.org** — Scottish Gaelic Wiktionary dump; ~17,000 lemmas with definitions, forms, IPA, and etymology
- **Dwelly's Gaelic-English Dictionary** — OCR text; ~55,000 additional entries
- **Akerbeltz.org** — 342 grammar rules across syntax, morphology, phonology, and related categories
- **scottish_gaelic-arcosg-ud-2.5** — UDPipe model used to parse 1,200 example sentences into CoNLL-U format


## Setup

1. Clone the repository
2. Ensure Go 1.22+ is installed
3. From the project root, run: `go run ./cmd`
4. Open `http://localhost:8080` in your browser

*Note for the grader: some Python is included in the repository, but it is not part of the setup. It is only there to show how the project's data was gathered, and is not meant to be run by the user.*


## Known Limitations

- Some Dwelly entries are proverbs or phrases imported as word entries due to the source format
- Other data inconsistencies derived from varying data policies across sources
- The web server structure does not yet account for multiple language modules
- No user accounts or progress tracking or lessons of any form in this version


## Roadmap

- User accounts and progress tracking
- Personalized lessons and lesson plans
- CEFR difficulty tagging for more than just rules
- Expression and idiom support
- Repopulate lower quality data entries to match the standards of kaikki
- Expand grammar ruleset towards comprehensive coverage and verify rules manually for accuracy
